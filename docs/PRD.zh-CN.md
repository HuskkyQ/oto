# TeslaMate Viewer — 产品需求文档（v1）

状态：草案，2026-11-02 · 负责人：Steven · 平台：iOS 17+（iPhone），只读

本文档定义 **v1 必须做到什么，以及如何判定做到了**。视觉与交互细节见
[`UI-DESIGN.zh-CN.md`](UI-DESIGN.zh-CN.md)，接口契约见 [`API.md`](API.md)，此处不重复。
English version: [`PRD.md`](PRD.md)。

---

## 1. 问题

TeslaMate 已经在记录实时遥测和完整历史，但它的 Web UI 是桌面仪表盘：需要浏览器、需要局域网
或 Tailscale 地址、需要宽屏。想用手机确认「车锁了吗、电够不够出发」，得在一张 Grafana 风格的
页面里翻找。

这个 App 把它换成三个问题，按顺序回答：

1. **车现在怎么样？** —— 当前状态、电量、续航、位置、安全。
2. **车最近去了哪、充了多少？** —— 行程与充电记录，是可读的日志，不是数据倾倒。
3. **长期趋势如何？** —— 7/30/90 天的里程、能耗、费用、轨迹。

## 2. 用户

一个用户（车主本人），一辆车，一台跑 TeslaMate 的 Mac。没有账号体系、没有分享、没有多租户。
这个人通常站在车边或坐在沙发上，单手拿手机。

驱动需求的场景：

| # | 场景 | 屏幕 |
|---|---|---|
| S1 | 准备出发：锁了吗、电够吗、车在哪？ | 实时 |
| S2 | 刚停好车：这趟用了多少电？ | 行程 → 行程详情 |
| S3 | 公共充电桩：现在充多快、什么时候满？ | 实时（充电中卡片） |
| S4 | 月底：开了多少、充电花了多少？ | 统计 |
| S5 | 「周六我去哪了？」 | 历史轨迹 |

## 3. 目标与成功标准

| 目标 | 成功标准 |
|---|---|
| 快速回答 S1 | 通过规划中的公网 HTTPS 代理冷启动后 1.5 s 内显示实时数据 |
| 实时要像实时 | 屏幕激活期间，MQTT 新值到达后 5 s 内反映到界面 |
| 历史要能扫读 | 任何列表/详情从所属 tab 出发 ≤ 2 次点击可达；接口返回后首屏渲染 < 300 ms |
| 绝不误导 | 任何屏幕都不会把 0、"—" 或过期数据呈现为当前真实状态（见 §5.7） |
| 构造上安全 | App 无法写入 TeslaMate；VIN、数据库口令、MQTT 凭据永不进入手机 |

## 4. 范围

v1 包含：

- 引导页、设置（服务器地址、Token、车辆、地图偏移、退出登录）
- 实时状态：轮询、充电卡片、导航卡片
- 行程列表（7/30/90 天）+ 行程详情（地图与图表）
- 充电列表（7/30/90 天）+ 充电详情（曲线）
- 统计（7/30/90 天，按日/按月）与柱状图
- 历史轨迹地图，从行程页与统计页进入
- 三个界面的地图：实时位置、行程折线、历史轨迹；含 WGS-84 → GCJ-02 校正、不申请定位权限、
  不缓存离线切片（FR-9）
- Mac 上的只读 Node API；iPhone 携 Bearer Token 经 HTTPS 访问规划中的公网固定域名反向代理，代理再经 Tailscale 访问 API，手机无需安装 Tailscale

v1 不包含（另见 UI-DESIGN §8）：

- 任何车辆指令（锁车、空调、充电控制）—— API 在设计上就是只读的
- 推送、小组件、实时活动、Apple Watch
- 多车界面（接口支持多车，v1 只选一辆）、多用户
- iPad/横屏、Android、Web
- 离线地图切片；只缓存最后一次成功响应
- 报警历史、地理围栏编辑
- 除 km / kWh / °C 以外的单位

属于「延后」而非「不做」：实时页上逐门反映状态的车辆 3D 模型（§10，DF-1），以及手动记录一次
非官方充电的实际花费（§10，DF-2）。

## 5. 功能需求

需求编号是测试与评审的稳定引用。"AC" = 验收标准。

### 5.1 引导 — FR-1

- FR-1.1 首次启动、或清除 Token 后，显示引导页而不是 tab。
  **AC** 看不到 tab bar；服务器地址与 Token 两个输入框都在。
- FR-1.2 「测试并保存」校验地址的 scheme/host，把 Token 写入 Keychain，并在进入 App 前调用
  `GET /v1/cars`。**AC** 非法地址、401、超时各自给出对应提示（UI-DESIGN §4.1）；返回 200 时
  显示车辆数量并进入 App。
- FR-1.3 Token 永不写入 `UserDefaults`、日志或源码。**AC** Keychain 是唯一存储；`SettingsStore`
  只持久化地址、车辆 id 和地图偏移开关。

### 5.2 设置 — FR-2

- FR-2.1 修改服务器地址或 Token 时，使用与引导页相同的校验规则。
  **AC** 校验失败不会覆盖当前可用的配置。
- FR-2.2 切换车辆时清空所有缓存响应并重载全部 tab。
  **AC** 上一辆车的数据不会残留在界面或缓存中。
- FR-2.3 「清除 Token」属于破坏性操作，需要二次确认，确认后回到引导页。
  **AC** 确认后 Keychain 条目已删除，App 无法再发起请求。
- FR-2.4 中国区默认开启地图坐标偏移校正，并且是用户可见的开关。
  **AC** 切换开关会重新渲染地图，但不重新请求数据。

### 5.3 实时 — FR-3

- FR-3.1 `scenePhase == .active` 时每 3 s 轮询 `GET /v1/cars/:id/live`。
  **AC** 后台或离开该 tab 时不再发请求；回到前台立即刷新一次。
- FR-3.2 下拉刷新始终可用，并与轮询共存。
  **AC** 手动刷新不会取消或重复 3 s 周期。
- FR-3.3 充电状态下，在电量与地图之间插入充电卡片（功率、已充电量、当前 SoC → 上限、充满时间）。
  **AC** 卡片随 `charging_state` 出现/消失，且不会因为布局变化把电量数字挤出首屏。
- FR-3.4 有导航目的地时追加导航卡片；`{"error":"No active route available"}` 视为「没有导航」，
  不是错误。**AC** 未设置导航的车辆不出现错误横幅。
- FR-3.5 安全行显示车锁、哨兵、车窗、车门；任一为「开」时该条目变橙，整行可点开详情。
  **AC** 单个 `false` 值即可改变该条目颜色并使整行可点击。
- FR-3.6 「最后更新」时间始终可见。**AC** 每次轮询成功都会更新；轮询失败时不会倒退。

### 5.4 行程与行程详情 — FR-4

- FR-4.1 列表默认最近 30 天，提供 7 / 30 / 90 切换。
  **AC** 切换会重新请求，并把滚动位置置为新结果顶部。
- FR-4.2 行按天分组并带吸顶日期头；地理围栏名称优先于地址。
  **AC** 两者都存在时只显示围栏名称。
- FR-4.3 分页使用 `limit=100`，滚动到 80% 时加载下一页，结束显示「没有更多行程」。
  **AC** 跨页无重复行；请求进行中不会发出第二个请求。
- FR-4.4 汇总条（里程、次数、时长）由已加载的当前页在客户端计算，不来自接口汇总。
  **AC** 汇总值与可见行之和一致。
- FR-4.5 详情页渲染地图折线、速度/功率/电量三张共享时间轴的图表，以及事实区块。
  **AC** 图表 x 轴范围一致；没有位置点的行程显示错误横幅并可返回，绝不空白页。
- FR-4.6 能耗 = `energy_kwh / distance_km × 100`，里程 < 0.5 km 时隐藏，< 18 绿色，≥ 18 橙色。
  **AC** 17.9 / 18.0 两个边界值的颜色符合规定；短途隐藏徽章。
- FR-4.7 仅当 ≥ 30% 的点有海拔数据时才显示海拔图。
  **AC** 关闭地形数据的行程完全不出现该图表。

### 5.5 充电与充电详情 — FR-5

- FR-5.1 时间段控件与分页规则与行程一致。
- FR-5.2 每行显示 SoC 进度条、kWh、时长与车外温度。
  **AC** 没有费用字段的会话显示「费用未记录」，绝不显示「¥0.00」。
- FR-5.3 详情页渲染功率、SoC、已充电量三条曲线，并用最后一个有效样本提供电压、电流、相数、
  连接器类型。**AC** 样本全为空时仍显示已有事实、省略曲线，不崩溃。

### 5.6 统计 — FR-6

- FR-6.1 时间段（7/30/90 天）与粒度（日/月）位于顶部栏下方同一内容行。
  **AC** 修改任一项都会重新请求，且不重置滚动位置。
- FR-6.2 卡片展示 `stats` 汇总的总里程、行程次数、充电电量、充电费用。
  **AC** 数值与同区间接口总计一致；区间内没有任何费用记录时显示「—」。
- FR-6.3 图表对无数据的日期补零，并与其它图表共享 x 轴。
  **AC** 有断档的区间显示连续柱状，坐标轴不被压缩。
- FR-6.4 点击柱子 **不在** v1 范围内。**AC** 柱子不可点击。

### 5.7 历史轨迹 — FR-7

- FR-7.1 历史轨迹不是 tab；从行程页（「轨迹」）和统计页的地图卡片推入，返回键回到来源 tab。
  **AC** tab bar 始终只有五项。
- FR-7.2 时间段选择器只作用于历史轨迹页，不改变行程/统计页的状态。
- FR-7.3 降采样请求 30 天用 `max_points=2000`，90 天用 `5000`。
  **AC** 请求 URL 符合规定；接口返回 400 时显示错误横幅，而不是空白地图。
- FR-7.4 汇总里程按显示点做 haversine 计算，并标注「约」。
- FR-7.5 空区间隐藏地图，显示「该时间段没有位置记录」。

### 5.8 通用行为 — FR-8

- FR-8.1 **新鲜度。** `stale == true` 且状态非休眠时显示橙色横幅；休眠车辆显示中性的
  「车辆休眠 · 数据停在 …」。**AC** 两种情况都不会在没有标注的情况下被当作当前真实状态。
- FR-8.2 **缓存。** 每个屏幕缓存最后一次成功响应，断网时展示并标注其时间。
  **AC** 关掉 API 后 App 仍可用且明确标注离线。
- FR-8.3 **401。** 每个屏幕只处理一次，提供「去设置」入口，不进入自动重试循环。
- FR-8.4 **空态** 必须带一个动作（切换时间段、重试），绝不伪造数据。
- FR-8.5 **加载。** 首次加载显示骨架屏；后续加载保留已有内容并显示小转圈。

### 5.9 地图 — FR-9

四个界面有地图，其余没有。在每一个界面上，地图都是该页已用文字说明过的数据的第二种呈现，
绝不是唯一的信息载体。

- FR-9.1 **出现位置。** 实时页显示最后已知位置；行程详情显示单次行程的折线；历史轨迹显示所选
  区间的轨迹；统计页只有入口卡片、不含地图。**AC** 其它页面不实例化地图；统计页的卡片以当前
  时间段打开历史轨迹页。
- FR-9.2 **坐标系。** 接口与存储均为 WGS-84。仅当 `mapOffsetCorrection` 开启**且**点位于中国
  境内时才在渲染前转换为 GCJ-02，境外不做任何处理。**AC** 开关开启时，已知坐标落在正确道路上；
  关闭时以一致的方向偏移约 500 m；切换开关只重新渲染，不发起任何网络请求。
- FR-9.3 **相机。** 所有地图打开时按内容自适应，四周留白 ≥ 12%，俯仰 0，不旋转。实时页仅在用户
  尚未拖动地图时跟随新位置；拖动后出现回中按钮，跟随停止，直到点击回中。行程详情与历史轨迹
  永不自动移动。**AC** 打开行程时整条折线都在画面内；行驶中拖动地图不会弹回；回中按钮恢复
  视角并继续跟随。
- FR-9.4 **线与标记。** 轨迹只用一条线；起点与终点标记靠**形状**区分，而不是只靠颜色。v1 不含
  充电桩标记、地理围栏、聚合。**AC** 灰度下起终点仍可区分，且各自带标注。
- FR-9.5 **不申请定位权限。** App 从不请求用户位置，也不绘制用户点。**AC** 构建产物的 Info.plist
  中不存在任何 `NSLocation*` 键；任何地图界面、首次或后续使用都不会弹出授权框。
- FR-9.6 **数据量。** 客户端按收到的降采样结果直接绘制，绝不对原始位置做聚合。**AC** 5 000 点
  轨迹在支持的最旧机型上拖动与缩放保持 60 fps。
- FR-9.7 **空、错、离线。** 区间内没有位置时整体隐藏地图框，显示一条提示带一个动作；接口 400
  时显示横幅并保留上一次状态；离线时在空白切片上绘制缓存轨迹，并标注其时间。
  **AC** 三种情况都不会出现没有任何解释的空地图框。
- FR-9.8 **无障碍。** 每张地图都有文字替代，包含里程与起终点名称。**AC** VoiceOver 能播报摘要，
  且地图上可见的每个事实在地图之外都有文字呈现。
- FR-9.9 **样式。** 标准地图、无起伏、无路况、无 3D。**AC** 所有界面与 UI-DESIGN §7 一致。

## 6. 非功能需求

| ID | 需求 | 验收 |
|---|---|---|
| NFR-1 | 只读 | Postgres 角色仅 `SELECT` 且无权访问 `private`；App 也无法发起变更，因为不存在这类接口 |
| NFR-2 | 传输 | iPhone 使用 Bearer 鉴权经 HTTPS 访问公网固定域名反向代理；代理经 Tailscale 访问 Mac API。Mac API 不直接暴露公网，手机无需 Tailscale |
| NFR-3 | 机密 | Token 只存在 Keychain；VIN、数据库与 MQTT 凭据不由接口返回，也不写入日志 |
| NFR-4 | 请求成本 | 每客户端 120 次/分钟，`/live` 单独 60 次/分钟；3 s 轮询为 20 次/分钟，叠加手动刷新也不会触发限流 |
| NFR-5 | 性能 | 实时页冷启动可交互 < 1.5 s；列表/详情在响应到达后首屏渲染 < 300 ms；滚动保持 60 fps |
| NFR-6 | 数据量 | 90 天轨迹为单次降采样响应（≤ 5 000 点）；客户端不对原始位置做聚合 |
| NFR-7 | 可靠性 | API 重启后 App 能自行恢复（下一次轮询成功）；过期数据始终带标注，绝不静默信任 |
| NFR-8 | 无障碍 | 支持动态字体、图表与电量环有 VoiceOver 标签、点击目标 ≥ 44 pt、遵循减弱动态效果 |
| NFR-9 | 本地化 | v1 中文优先；所有文案外部化，做英文时无需改动布局 |
| NFR-10 | 兼容性 | iOS 17+，仅 iPhone 竖屏，仅深色 |

## 7. 依赖与约束

- TeslaMate 的表结构与 MQTT topic 命名属于外部契约。TeslaMate 升级若改了 topic 名，实时页应
  优雅降级（缺值就不显示，而不是报错）。
- 规划中的公网反向代理必须可通过 HTTPS 访问，并能经 Tailscale 连接 Mac API；手机无需 Tailscale。没有云端数据回退。
- 里程与能耗以 TeslaMate 的数字为准，App 不得用另一套算法重算（历史轨迹的 haversine 已明确标注「约」）。
- `max_points` 上限由接口强制（10–5000），客户端不可假设更多。

## 10. 延后（v1 之后）

原则上已确定、但 **v1 不实现** 的需求。它们使用 `DF-` 编号，以免被误认为 v1 承诺，也不计入完成度
统计。

### DF-1 实时页车辆模型 —— 延后，无排期

在实时页用一个车辆的 3D 模型，逐部件反映状态：四扇车门、后备箱、前备箱、充电口盖的开合与实车
一致。数据侧已经具备——`/live` 已输出 `driver_front_door_open`、`trunk_open`、
`charge_port_door_open` 及其同类字段——所以这是表现层问题，不是后端问题。

- DF-1.1 **范围。** 模型替换或并列于电量环，并在一个轮询周期（约 3 s）内同步部件状态。
  **AC** 实车打开任意车门后 5 s 内，模型上可见。
- DF-1.2 **渲染。** RealityKit + `RealityView`（iOS 17 目标版本即可用）、USDZ 资产、按需渲染。
  SceneKit 自 iOS 26 起废弃；three.js / `WKWebView` 方案不予采用（多一个运行时、持续帧循环、
  冷启动更重）。
- DF-1.3 **资产。** 逐部件节点、铰链枢轴正确；1 单位 = 1 米、Y 轴向上；材质按深色调色板制作 PBR；
  必须获得授权——不得使用特斯拉官方模型或渲染图。**AC** 在 Blender 中每扇门为独立对象，
  且绕铰链旋转。
- DF-1.4 **未知状态。** 字段为 `null` 时，绝不把部件动画成关闭状态；部件保持上一次已知姿态，
  界面按常规新鲜度规则处理（FR-8.1）。
- DF-1.5 **开销。** 场景只构建一次，每次轮询只修改节点，绝不重建；不得使 NFR-5 倒退。
- DF-1.6 **退路。** 若拿不到带铰链的资产，改为给打开的部件染色而不是让它移动——同一套数据、
  同一套布局、无需绑定。

未解决、也正是延后原因的问题：

- **远侧可见性。** 3/4 视角下，左后门被车身挡住。可选方案是相机自动转到开门侧、加俯视小图，
  或接受「安全行仍是唯一真相来源」。三者均未选定。
- **粒度。** 车辆只上报布尔值：没有「虚掩」，也没有车窗开度。
- **资产成本。** 模型、枢轴与材质才是主要工作量，不是代码。

### DF-2 非官方充电站的费用 —— 延后，仅手动录入

车在一家 Oto 没有价格的充电站充电，充完之后运营商的完成通知里带着金额。这条通知永远不是输入：
iOS 没有读取其他 App 通知的公开 API，通知服务扩展与信息过滤扩展也都不允许保存或转发内容。
所以唯一的路是由用户给出这个数字，这里要做的是把这一步变得几乎不费力。

会话的电量、时长、起止时间与位置 Oto 都已经有了，唯一无法推导的就是金额。

- DF-2.1 **入口。** 充电详情页只放一个动作「记一笔费用」。**AC** 从会话一键可达；已经有费用的
  会话直接显示费用，不显示该动作。
- DF-2.2 **默认值。** 表单把该会话的 kWh、时长、站点与开始时间作为只读上下文展示；金额是唯一的
  输入，另有一个可选备注。**AC** 没有任何字段要求用户重新输入 Oto 已有的值。
- DF-2.3 **剪贴板预填。** 当剪贴板里恰好是一个金额（如 `¥45.60`、`45.6元`）时，金额字段打开即
  预填，且在保存前始终可见、可编辑。**AC** 没有明确金额的文本不会填任何东西；没有明确点击就不会
  保存。
- DF-2.4 **来源标注。** 手动录入的金额始终标注为手动，绝不以 TeslaMate 的数字呈现。
  **AC** 充电列表行与详情页都带这个标记。
- DF-2.5 **合并规则。** TeslaMate 的 `cost` 与手动金额绝不静默相加；两者都存在时以接口为主，
  手动金额标注后显示在其下方。**AC** 两者都可见且可区分，统计总数绝不把两者相加。

未采用的方案及原因：

- **分享账单做 OCR。** 能拿到真实账单，但需要自己的页面、一次确认和逐家解析——在剪贴板预填存在
  之后，它换来的价值抵不上这份工作量。
- **运营商接口。** 没有公开的。
- **读取完成通知。** 在 iOS 上做不到，不是难做。
- **地理围栏计价。** TeslaMate 自己的 `cost_per_unit` / `session_fee` 对固定站点仍是更好的答案，
  且完全不需要 Oto 写代码——这一项存在的意义，是那些按单价算下来对不上账单的站点。

未解决、也正是延后原因的问题：

- **金额存在哪。** Oto 在构造上是只读的（NFR-1、只读角色、没有变更接口）。把手动录入的费用存在
  Oto 自己的库里能保住这条，但会造出两个真相源：统计总数要把本地金额与接口总计合并，而之后又
  拿到 TeslaMate 费用的会话还要对账。另一条路——加一个只 `UPDATE charging_processes.cost` 的
  窄接口——只有一份数字，但会打破 NFR-1。尚未决定，而它决定这一项能否开始。
- **填错了就永久存在。** 手动录入没有电量或单价做交叉校验，一个手误与历史记录之间只隔着一次确认。
